# S04: Reliable Scripture chat with correct stream settlement

<!-- visibible-modernization:S04 -->

## Problem Statement

A chat error can arrive as ordinary stream data and still trigger a charge. Cancellation, input trust and long histories are not enforced through one coherent chat interface.

## Solution

Provide bounded, passage-grounded chat that reports a clear outcome and settles credits according to actual stream success.

## User Stories

1. As a guest, I want to receive an answer about my selected passage, so that chat stays connected to reading.
2. As a guest, I want to avoid a charge for a failed stream, so that errors do not consume my credits.
3. As a guest, I want to cancel a response, so that unwanted work stops and follows the published billing rule.
4. As a guest, I want to see accurate token and charge metadata, so that I understand each completed turn.
5. As a guest, I want to receive a clear limit message for an oversized conversation, so that the request fails before paid work.
6. As an operator, I want to measure spend on failed and cancelled turns, so that subsidized costs remain visible.
7. As a maintainer, I want to test the installed SDK error format, so that stream-library changes cannot silently alter charging.
8. As a guest, I want to receive server-grounded Scripture context, so that another client payload cannot replace the app instructions.

## Implementation Decisions

- Keep streaming chat in Next.js for this program. Put admission, server-owned passage context, stream outcome and credit settlement behind one chat interface. Persistent conversations are out of scope.
- An accepted success requires nonempty assistant text, no provider error, and an allowed stop or length finish. Label length-limited output as incomplete but chargeable. Empty, error and cancelled outcomes release customer holds; always retain known provider spend.
- Wire the request abort signal to provider streaming and cancel the active reader correctly. Settle once under completion/error/cancel races. After a terminal success is recorded, a late disconnect does not reverse the charge.
- Only the server supplies system instructions. Accept user and assistant history with explicit role/part validation; resolve passage text from canonical reference and translation. User content cannot become a privileged system message.
- Calculate admission from bounded serialized input and selected model limits. Enforce a default maximum of 2,048 output tokens, also constrained by model context/capabilities and accepted quote. Make truncation or rejection visible instead of silently dropping meaningful history.
- First repair incorrect units and stream outcomes on the existing route. Integrate versioned quote caps and durable receipts after the wallet changes, without delaying the independent correctness fixes.
- Any context, SDK or model-behavior change must pass the existing chat evaluation release rules as well as mechanical tests. If candidate evaluation does not pass, retain the baseline and record the result.

## Testing Decisions

Tests assert externally observable behavior through the highest practical existing interface. Exercise actual application handlers and replace external paid/network effects with controlled adapters. Avoid tests that repeat implementation arithmetic or only inspect source text.

- Use the real installed AI SDK with a fake model provider; include errors encoded as UI stream parts that close normally.
- Test normal stop, length finish, empty output, exception, cancellation and cancellation racing completion through the chat interface.
- Assert stable balance/ledger effects, not TransformStream internals or source text.
- Use existing credit-flow tests for prior behavior and S10 evaluations for answer quality.

## Out of Scope

- Persisted chat history
- Tools or retrieval beyond canonical passage context
- A redesigned chat persona
