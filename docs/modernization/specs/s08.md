# S08: Reliable shared image storage and bounded library reads

<!-- visibible-modernization:S08 -->

## Problem Statement

Image insertion can race, remote fetching has gaps, and gallery/count queries grow with all historical images. Readers need durable images without loading unbounded history.

## Solution

Give each saved image a stable identity, safe storage and provenance. Serve summaries and paginated history while preserving public image responses.

## User Stories

1. As a reader, I want to browse saved images for a verse, so that I can compare prior illustrations.
2. As a reader, I want to open a saved-image link, so that I see the same image after navigation or refresh.
3. As a reader, I want to browse a large chapter gallery, so that history size does not make the page unusable.
4. As a reader, I want to see image counts and latest images, so that I can find illustrated passages quickly.
5. As a guest, I want to see whether output is durably saved, so that I know whether I can return to it.
6. As an API consumer, I want to keep using existing image endpoints, so that the internal refactor does not break my integration.
7. As an operator, I want to save provider output without duplicate rows, so that retry processing is safe.
8. As an operator, I want to limit remote image fetch destinations and size, so that external URLs cannot bypass storage restrictions.

## Implementation Decisions

- Image insertion enforces generation identity inside its transaction. Storage retries reuse persisted bytes or a recoverable provider result. Clean up orphaned storage blobs through a bounded verified process; never delete a blob still referenced by an image.
- Prefer provider-returned bytes. Remote fetch remains an adapter with HTTPS/allowlist validation, controlled redirects, MIME/size/time limits and a verified strategy against DNS rebinding/private destinations. Default to no redirects; enable a redirect only with destination validation. If the runtime cannot safely constrain resolution, reject that URL path rather than claim protection.
- Separate generation lifecycle, planner cache, storage and library read implementations under small interfaces. Public outputs are explicit projections; private ownership data, prompts and financial fields remain excluded from the public API contract.
- Keep old image IDs, public routes and storage URLs working. Use additive metadata for translation, model, prompt version, source generation and durable-storage state. Legacy URL-backed rows remain clearly identified.
- Paginate reader history and gallery with stable cursor ordering. Default page size 30, max 100. Keep selected-image lookup independently addressable so pagination cannot break deep links.
- Maintain verse/chapter/book availability summaries transactionally with image insert/delete operations. Backfill summaries in resumable batches and compare against reference queries before switching consumers.
- Measure impression-driven invalidation first; move high-write impression counters away from image records when representative testing shows needless history/gallery recomputation. Publication ranking uses a dedicated count projection defined in S11.

## Testing Decisions

Tests assert externally observable behavior through the highest practical existing interface. Exercise actual application handlers and replace external paid/network effects with controlled adapters. Avoid tests that repeat implementation arithmetic or only inspect source text.

- Test save/read/public projection at their interfaces with real mutations and fake storage/fetch responses.
- Concurrently save one generation and assert one image row; verify unused blobs are not mistaken for referenced ones.
- Test pagination with repeated timestamps, insertion between pages, absent selected images and historical IDs.
- Exercise blocked redirects, private destinations, oversized bytes, misleading MIME and timed-out bodies.

## Out of Scope

- Private image collections
- New public API features
- Deleting legacy images solely to simplify the schema
