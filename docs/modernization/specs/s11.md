# S11: Trustworthy publication, operations and retention

<!-- visibible-modernization:S11 -->

## Problem Statement

Publication ranking trusts raw public increments, operational counters reset with each process, and cleanup does not express a consistent retention policy.

## Solution

Give operators durable summaries of work and reconciliation, bounded publication ranking and explicit cleanup rules.

## User Stories

1. As an operator, I want to see unresolved generations and invoices after restarts, so that I can repair incomplete work.
2. As an operator, I want to compare provider spend and guest charges, so that I can find unexpected subsidy or pricing drift.
3. As an operator, I want to know what readiness actually checked, so that a green response is not mistaken for live provider health.
4. As a reader, I want to see selected Scripture images shared to Nostr, so that the public library reaches others.
5. As an operator, I want to avoid repeated publication after a relay timeout, so that recovery does not spam relays.
6. As a reader, I want to have repeated views counted fairly, so that one browser cannot inflate a publication candidate without limit.
7. As a guest, I want to read accurate privacy and credit notices, so that I understand stored data and session limitations.
8. As an operator, I want to run bounded cleanup without erasing financial evidence, so that maintenance remains safe.

## Implementation Decisions

- Use durable operation/receipt/invoice records for business metrics and unresolved-work views. Process counters can remain labeled local diagnostics; aggregate operational rates with suitable log/metric storage rather than summing arbitrary server snapshots.
- Keep public health/readiness responses minimal. Report liveness, configuration readiness and last successful dependency observation separately. Dependency probes run on bounded schedules, never paid generation; authorize detailed operational output.
- Default retention: preserve credit ledger, settled invoice evidence, positive balances, unresolved attempts, stable operation dedupe identities and Nostr publication IDs. Keep detailed completed job/operation diagnostics 90 days and processed outbox payloads 30 days, while retaining compact receipts and dedupe keys. Expire unused scene plans after 90 days; retain original saved-image provenance. Retention changes require an impact review and dry run, not an unbounded deletion.
- Session access expiry does not authorize deleting funded records. Abandoned zero-balance sessions are eligible only after 90 days and after checking all linked unresolved/financial state. Feedback raw user-agent/IP context is minimized; retain feedback text/context for 180 days unless operational need is explicitly recorded.
- Keep latest-completed-four-hour-window Nostr cadence and at-most-one selection. Do not backfill missed windows automatically. Choose at most one eligible impression per authenticated guest/image/window for ranking, with a bounded write rate; treat it as abuse resistance, not proof of unique humans. Views remain public.
- Persist the signed Nostr event ID before publishing. Retry only the same signed event when safe; record relay acknowledgements and never create a new event solely because local recording failed. Preserve the current conservative handling of ambiguous historical windows.
- Privacy and credit copy must cover feedback context, sessions, preferences, invoices, images, analytics, access expiry and actual persistence guarantees. No legal retention-compliance claim is made by this engineering policy.

## Testing Decisions

Tests assert externally observable behavior through the highest practical existing interface. Exercise actual application handlers and replace external paid/network effects with controlled adapters. Avoid tests that repeat implementation arithmetic or only inspect source text.

- Recreate an operator process and verify unresolved-work and spending summaries are still available.
- Test unauthorized detailed probes, dependency outages and old observations without paid calls.
- Inject relay success followed by failed recording, partial relay acknowledgement and downtime; assert stable event identity.
- Run cleanup dry runs on synthetic linked data and verify no retained balance, financial record, pending task or referenced image is deleted.

## Out of Scope

- A social feed or voting system
- New relay platforms
- Automatic replay of missed publication windows
