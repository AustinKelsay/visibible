# S12: Verified migration and retirement of old implementations

<!-- visibible-modernization:S12 -->

## Problem Statement

A broad replacement can lose subtle reader behavior, hide untested modules or split financial truth between old and new execution.

## Solution

Keep a traceable acceptance inventory, test public behavior and migrate in reversible slices with one executor and wallet per operation.

## User Stories

1. As an existing reader, I want to keep my URLs and saved images, so that the replacement preserves useful work.
2. As a guest, I want to keep my balance and purchase history, so that migration cannot erase or duplicate credits.
3. As a maintainer, I want to see all 86 investigation items mapped to tickets, so that work does not disappear through grouping.
4. As an implementer, I want to take one bounded ticket with explicit blockers, so that I can complete a verifiable slice.
5. As a reviewer, I want to see relevant behavior tests and coverage gaps, so that passing CI reflects meaningful confidence.
6. As an operator, I want to restore data and switch execution safely, so that rollout problems have a tested recovery path.
7. As a maintainer, I want to delete the replaced code when safe, so that migration reduces long-term complexity.
8. As a future agent, I want to find current behavior and decisions, so that documentation stays useful after code moves.

## Implementation Decisions

- Keep every original backlog ID traceable to a primary spec and one or more tickets. A verification ticket can close with measured evidence and a justified no-change result; it cannot close with an unexecuted plan.
- Capture acceptance cases for existing reader URLs, translations, keyboard/touch navigation, gallery/deep links, free browsing, credits, Lightning, public API and Nostr. Source-text tests are replaced only when their meaningful behavior has equivalent coverage.
- Use real Convex handlers for ownership, ledger, invoices, jobs, receipts and insertion; fake only external effects at the adapter seam. Include production modules in coverage and explicitly baseline newly exposed gaps rather than lowering standards to hide them.
- Create a protected export/restore and reconciliation procedure before data mutation. Use synthetic/local data by default. A live rehearsal requires the correct deployment identity and established release authority; this planning task does not access production secrets or data.
- Expand schema additively, migrate with resumable checkpoints, reconcile counts/balances and preserve identifiers. Each admitted operation stores executor/policy version. Old in-flight work drains under its original executor while new admissions can switch. Never dual-execute paid work or maintain two balances.
- Roll out by bounded session cohort after preview acceptance; a stop switch closes new admissions without cancelling recorded settlement/reconciliation. Rollback preserves newly created records, drains or resolves in-flight work, and never replays completed provider calls.
- Remove old implementations only after caller inventory, migration verification and rollback rehearsal demonstrate no required dependency remains. Preserve compatibility adapters for external URLs and existing records until their contract permits retirement.
- Update feature docs in the same ticket as changed behavior. The final documentation ticket checks consistency; it is not permission to defer all docs until the end. Existing guides remain authoritative for shipped behavior; specs describe intended behavior.
- Complete repo-required lint, type checks and relevant tests per implementation slice. Visible changes include browser checks/screenshots. Model changes also use S10 evaluation requirements.

## Testing Decisions

Tests assert externally observable behavior through the highest practical existing interface. Exercise actual application handlers and replace external paid/network effects with controlled adapters. Avoid tests that repeat implementation arithmetic or only inspect source text.

- Use a synthetic pre-migration database with balances, old images, active reservations, pending invoices and Nostr records.
- Verify upgrade, restart, interrupted backfill, mixed executors and rollback, comparing financial totals and public contracts.
- Exercise end-to-end recovery for duplicate requests, provider ambiguity, late payments, storage failure and tab closure.
- Validate ticket dependency graph and complete backlog coverage before publication.

## Out of Scope

- Implementing the full program during the specification task
- Deleting production data to simplify migration
- A second permanent application or credit ledger
