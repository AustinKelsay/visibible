# Analysis storage

A work's **analysis** is everything the engine makes for it: story sections, moments and entries (canon with stages), plus reference images and attention items. Owner-authored inputs (the work file, the approved brief and the style library) are repo files; the analysis is per-deployment Convex data in [analysis.ts](../../convex/analysis.ts) and never copied between deployments. Saved images and generation requests keep their existing tables.

## Records and versions

Every analysis record carries its work ID, the generation it belongs to, a stable record ID, a content-hash **version** of its payload ([contentVersion.ts](../../convex/_helpers/contentVersion.ts)), a `generated` or `owner` **source**, and the exact input versions it was made from. Stable IDs: entries by slug, sections and moments by their first unit. Records are never edited in place; a new version supersedes the old one, and superseded or retired versions stay readable through `getRecordVersion` and `listRecordHistory` for provenance. Sections and entries name no inputs, since they come from the work file and brief; references name the record versions they were made from.

Newly staged no-form canon also retains each stage's optional structured `showing` choices beside its complete `text`. These choices use the drafter's closed effect/color/brightness vocabulary. Rendering consumes the complete text. Historical stages remain valid without this field. Adding metadata changes the entry's content hash and invalidates its ordinary dependents; no live backfill or automatic redraft is performed.

## Generations and activation

A full reread is staged as a **candidate analysis generation** (`stageGeneration`, `putRecords`), distinct from a *generation* in the glossary's sense of one requested image. Only one candidate is open per work; staging another abandons it, and `abandonGeneration` gives one up explicitly. `activateGeneration` requires the open candidate, a match with the deployed work and brief versions registered by `registerWork`, and structural validity: sections and entries exist, sections and moments are anchored to their first unit, moments name existing sections, casts name existing entry stages, characters and locations have at most three stages and objects at most one, and any entry a cast uses has at least one stage (an entry that is only mentioned may have none). The check runs on what would actually serve, owner versions included, so an owner edit that no longer fits the reread blocks activation with the conflicting record named in the error. A failed or incomplete activation changes nothing, so the current active generation keeps serving.

For newly staged generations, `putRecords` validates each moment's first-unit anchor and section link. Stage sections before their moments, or include both in one atomic batch. Rewrites are counted once, and the server maintains generation record counts. Activation then checks entries, sections and any carried owner moments without scanning all fixed units. Candidates created before this protocol still receive the original full structural check.

On activation, owner versions from the previously active generation are carried forward where their record ID still exists; the rest become `unmatched_owner_edit` attention items. The serving pointer and previous generation status change atomically. Owner row statuses retire in that transaction; other historical row statuses catch up in bounded batches of 250. Historical records remain readable throughout, and generated images are untouched.

## Readiness

`getWorkStatus` reports `ready` only when an active generation exists and was read against the registered work and brief versions. A registered brief alone is not enough. Missing or failed reference images and open attention items do not affect readiness. Reads of the active generation (`getActiveRecord`, `listActiveRecords`) never return candidate records. Lists use a kind/status index; large enumerations use `listActiveRecordsPage`, capped at 500 records per page and pinned to the admitted generation. A pointer change refuses further enumeration so the caller can retry admission. The production prose-moment lookup and evaluation command consume these pages through `listAnalysisRecords`; fixed-unit requests keep their exact moment lookup. `getGeneration` reads maintained counts for new generations, including retired ones.

This avoids Convex's [32,000-document transaction scan limit and 8,192-element array limit](https://docs.convex.dev/production/state/limits) for the complete Bible's 31,102 moments plus sections and canon. Stale-dependency inspection (`listStaleDependents`) reads only current references, since no analysis record names another as an input, so it works on the full Bible. The destructive work-wide wipe still uses its original full scan; it is not part of activation or reader generation and is not certified for a full-Bible run.

## Corrections and staleness

`correctRecord` writes an owner version into the active generation; later rereads never overwrite it. `listStaleDependents` lists current reference images whose inputs name an older version of a record, for targeted remaking; nothing is regenerated automatically and saved images are never touched.

`addCastEntry` repairs a missing identity by adding one complete owner canon entry and appending its assigned stage to one existing section in a single transaction. It checks the registered work version, active generation, expected section version, entry-ID collision and stage completeness/counts. It preserves existing cast assignments and section history, increments the entry count once and accepts exact retries without duplication. The [owner command](../workflow/OWNER-CORRECTIONS.md) additionally verifies quotes against the imported reference text; the server receives trusted owner-authored text and does not independently load the work file. A reread carrying that owner section must also contain the new entry ID, or activation fails structurally while the old generation continues serving.

## References and attention

`putReference` records a sheet or style reference blob in Convex file storage with its inputs and a fingerprint of them; `getReference` reports whether the stored reference is stale against expected inputs, and a pinned reference (`pinReference`) is never stale and cannot be replaced until unpinned. `noteAttention` opens or re-counts an attention item by reason, kind and record; `closeAttention` records a disposition. Writes use the server secret like `saveImage`; reads are public queries.
