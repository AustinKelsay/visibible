# Image generation

[POST /api/generate-image](../../src/app/api/generate-image/route.ts) performs the OpenRouter request in Next.js. Convex tracks state, credits, cached scene plans and saved images; it is not a background worker for this request.

## Request lifecycle

1. Validate the feature flag, origin, CSRF token, signed session with current-IP tracking, body, model and rate limit.
2. Resolve the required single-verse reference and selected translation through [the canonical passage resolver](../../src/lib/generation-passage.ts). The reference endpoint resolves aliases; a validated canonical chapter supplies the text. Neighbors use the shared navigation rules. Client text, neighboring context and theme are compatibility fields only and never become prompt/cache input. Genesis 1 uses the server-owned theme. Missing/invalid current text and upstream failures stop before reservation or provider work; missing neighboring text is omitted, while neighboring lookup errors remain retryable.
3. Authenticated retries return the existing operation before catalog or Scripture reads. New requests query the scene plan by verse, translation and style; reuse also requires the full canonical-input fingerprint, prompt version and planner model. The fingerprint includes complete current/neighbor text, theme/style fields and the exact planner prompt. A lookup does not update hit counters; the separate hit mutation verifies the same identity so a delayed write cannot affect a replacement. Affordability (HTTP 402) and the daily spending limit (HTTP 429) are checked before the request is recorded, so a refused request does not consume its request ID; a retry with the same ID after a top-up, as bulk resume sends, is admitted normally. The reservation repeats both checks atomically to guard races. Atomically claim the owner/input fingerprint and billing ID before any paid work. Admission failure starts no provider call. A cache miss runs the optional planner with verified server inputs. If the planner model's pricing is unknown (missing or malformed catalog rates, or a failed pricing lookup), the request skips the planner and uses the direct verse prompt, so no unpriced provider work runs; a known-free planner still runs.
4. Assemble the bounded prompt, mark the request as generating, and call OpenRouter with the configured timeout.
5. Settle credits, persist the cost event (or enqueue its outbox fallback), attempt server-side image storage, and return the image and available saved-image ID. Failure to save does not imply that generation failed or that the image is permanently stored.

Lifecycle states are `queued`, `planning`, `generating`, `succeeded`, and `failed`. [verseImages.ts](../../convex/verseImages.ts) provides the lifecycle/cache/storage functions; [schema.ts](../../convex/schema.ts) defines their fields. [costs.ts](../../convex/costs.ts) handles Neutral Cost and outbox replay.

## UI and pricing

[HeroImage](../../src/components/hero-image.tsx) sends a request ID, subscribes to lifecycle status, and registers generation controls with [GenerationContext](../../src/context/generation-context.tsx). Header controls share that state. First-image auto-generation requires loaded empty history and strict affordability; explicit actions can use the spend-down grace. Empty history alone does not cause a paid request.

`/api/image-models` supplies per-resolution catalog quotes including the planner surcharge, plus timing information. Resolution support is normalized before lookup. The backend can quote less than the UI on a planner cache hit. [Sessions and credits](SESSIONS_AND_CREDITS.md) explains holds, settlement and fallback charges.

## Configuration and related behavior

- `ENABLE_IMAGE_GENERATION=true` enables the route. `ENABLE_SCENE_PLANNER=false` disables planning; planning is otherwise enabled.
- Timeout/model overrides are listed in [.env.example](../../.env.example); the route and [scene-planner.ts](../../src/lib/scene-planner.ts) define defaults. The planner request disables reasoning, because reasoning tokens count against its 220-token limit; a planner model must allow that (`openai/gpt-oss-*` does not). The [model comparison](../research/2026-10-14-scene-planner-free-models.md) explains the current default.
- A free planner model shares the OpenRouter account's free-model allowance: 20 requests per minute, and 1,000 per day for accounts that have bought at least $10 of credits (50 per day otherwise). Visibible's account had the 1,000 allowance on 2026-10-14. Reused scene plans make no request. When the allowance runs out, the planner gets HTTP 429 and generations continue without a scene plan until it resets; only very large bulk jobs are likely to reach it.
- Every generation that reaches planning records one `scene_planner_outcomes_total` count: `planned`, `cache_hit`, `disabled`, `skipped_unpriced`, `http_error`, `empty_content`, `invalid_plan`, `timeout` or `error`. A rise in anything but the first three means scene plans are being lost; see [Observability](OBSERVABILITY.md).
- [Prompt specification](../implementation/IMAGE_PROMPT_SPEC.md), [persistence](IMAGE-PERSISTENCE.md), and [bulk generation](BULK-GENERATION.md) cover those separate concerns.
- [Credit-flow](../../src/app/api/__tests__/generate-image/credit-flow.test.ts) and [scene-planner](../../src/app/api/__tests__/generate-image/scene-planner.test.ts) tests cover request behavior.

The canonical-input version boundary is `2026-09-08-canonical`. It prevents plans authored under the older client-text policy from being reused. Legacy entries without the full input fingerprint miss safely. One cache slot remains per verse/translation/style; a newer incompatible input replaces that slot rather than growing versions indefinitely. Saved image records and replay responses preserve the original reference, translation and verse text; existing historical images are not rewritten. The provider receives bounded canonical text with whitespace normalized, without removing words such as “instruction” from Scripture.

[Image prompts](../../src/lib/image-prompts.ts) owns scene-plan normalization, bounded image prompt construction, planner prompt construction, and cache fingerprinting. Its classical style strings, priority rules, trimming order, 180-character plan fields and 2,800-character image budget preserve the captured baseline. Model/prompt changes must update their declared version and follow the evaluation release policy.

## Catalog quotes and supported settings (T03)

[Image catalog](../../src/lib/image-catalog.ts) normalizes the general OpenRouter catalog for the existing chat-completion image request. It reads text input/output rates and `pricing.image_output` as USD per output token for the verified Gemini families; it never treats `pricing.image` as a generated-image price. Billing metadata contains its source, capture time, unit and policy version. Capabilities contain documentation provenance. The adapter does not switch generation APIs.

Generic reference images use the explicit `pricing.image` price when present. If it is absent for Gemini 3.1 Flash, Flash preview or Lite, the billing adapter uses Google's default 1,120 input tokens per reference at the catalog's unified text/image input rate. This is independent of output resolution. The policy version is `google-input-output-tokens-2026-10-20`; unknown input pricing and malformed explicit rates still refuse reference-bearing requests. [Google media token counts](https://ai.google.dev/gemini-api/docs/media-resolution), [pricing](https://ai.google.dev/gemini-api/docs/pricing) and [recorded provider usage](../releases/2026-10-20-disabled-engine/reference-pricing.md) support this normalization. Historical images and accepted request replays retain their original billing commitments.

Google documents 1,290 output tokens for Gemini 2.5 Flash Image. Gemini 3.1 Flash uses 1,120/1,680/2,520. Gemini 3.1 Flash Lite Image supports only 1K, at 1,120. Estimates additionally allow 1,000 text input and 1,000 text output tokens. These are estimation assumptions, not enforced spending caps. The combined decimal sum rounds to credits once. Sources: [Google image dimensions/token counts](https://ai.google.dev/gemini-api/docs/image-generation), [Google pricing](https://ai.google.dev/gemini-api/docs/pricing), [OpenRouter chat request contract](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request).

The verified registry covers the default, Gemini 3.1 Flash Lite Image; Gemini 2.5 Flash Image; and the Gemini 3.1 Flash stable and preview identifiers. The [image model comparison](../research/2026-10-14-image-models.md) explains the default and why Gemini 3 Pro was removed. The catalog leaves out models outside the registry until their output units and request settings are verified. Explicit unsupported settings fail before reservation/provider work. Stored resolutions normalize when selecting a model; a removed saved model requires an explicit new selection.

Discovery and admission use the same catalog quote. Discovery includes the planner allowance (zero when planner pricing is unknown); an existing compatible scene plan can reduce admission by that allowance. Cost samples are still recorded, but unversioned historical/model/provider/global estimates do not override current quotes. T05 introduces validated learned estimates. The model-list GET no longer starts a historical backfill.

A catalog outage may use a labeled last-known snapshot for at most six hours. Without one, choices are unavailable; the configured default is never inserted into a successful catalog that removed it. Selectors refetch when reopened. Scripture remains available during pricing failure.

Holds use the bounded headroom described in [Sessions and credits](SESSIONS_AND_CREDITS.md); final settlement still uses actual usage where available. A visible accepted maximum, input/output exposure bounds and versioned quote acceptance (T04) are not implemented. Historical charges are unchanged.

## Engine admission

Every new image request is bound to one engine at admission ([admission.ts](../../src/lib/engine/admission.ts)) and the binding is persisted on its `imageGenerationRequests` record (`engine`, `artStyleId`, and for the generic engine its `engineCommitments`: work, moment, brief version, analysis generation, prompt and billing versions). A replay of the same request returns the accepted engine and saved result and never reprices or switches engines; a request without an `engine` field is historical and legacy.

A request may name the engine it is bound to (`engine` in the body, sent by bulk jobs after their first accepted item); when admission would decide differently the route answers 409 "Engine binding changed" before any reservation or record, and the request id stays usable. Success and replay responses report `engine`. `GENERIC_ENGINE_MODE` selects the rollout stage: `disabled` (default) routes Classical to the legacy engine and reports Ink & Watercolor and Byzantine Icon as temporarily unavailable with a retryable 503, leaving saved style preferences untouched; `owner` admits the generic engine only for a session whose tier is `admin`, verified server-side, so the owner can prove it in production; `public` sends every new request to the generic engine. Generic admission also requires the work's analysis to be ready (`getWorkStatus`); when it is not, the request gets a retryable "Preparing scene" 503 rather than a legacy fallback. Optional references and open attention items never gate admission.

Generic dispatch goes through one seam ([dispatch.ts](../../src/lib/engine/dispatch.ts)) to the generic engine ([generation.ts](../../src/lib/engine/generation.ts)). Rollback is `GENERIC_ENGINE_MODE=disabled`: accepted generic requests keep their engine, new Classical requests use legacy, and the other styles report unavailable. The release, rollback and retirement steps, the rehearsal command and the evidence template are in the [engine release runbook](../workflow/ENGINE_RELEASE.md).

## Reader controls

The reader's art style ([Preferences](PREFERENCES.md)) goes with every request as `style`. `/api/image-models` reports `artStyles` with the same admission decision generation would make ([admission.ts](../../src/lib/engine/admission.ts)), so an offered style the server is not admitting is shown as temporarily unavailable, generation in it is disabled with a message, and saved images and the preference stay as they are; it is never silently replaced by Classical. While a non-Classical request has no request record yet the hero shows "Preparing scene…", and a retryable 503 (a scene still preparing, a style not admitted) is shown with the server's message and a retry. Variation numbers and auto-generation eligibility count only the selected style's images.

## Generic generation path

An admitted generic request runs, in order: the deployed work, brief and style files ([work-inputs.ts](../../src/lib/engine/work-inputs.ts), read once per instance and versioned like the owner scripts version them) must match the versions the active analysis was registered with; the verse's moment and section come from the active analysis and the moment text and in-section neighbours from the imported reference text, never from the reader's translation; the section look and scene plan are prepared lazily ([Scene preparation](SCENE-PREPARATION.md)); the plan's present entries supply canon stages; reference sheets and the style reference are used only when current for their entry, stage and style versions (or pinned) and when their bytes load, converted to JPEG and sent inline after the prompt; the rendering packet is built and validated ([prompt spec](../implementation/IMAGE_PROMPT_SPEC.md#generic-rendering-packet)); the prompt-aware quote is checked against the image envelope; affordability and the daily limit are checked; the request record is created with `engine: "generic"` and its commitments; the exact packet is persisted on the request (`renderingPacket`) before any paid attempt; credits are reserved (or the owner's audit entry written); one provider call is made; settlement, the cost event and the saved image follow the legacy contract.

Failures before the request record cost nothing and leave no request: inputs not deployed or mismatched, a missing moment, a look or plan that cannot be made (503 "Preparing scene", retryable, with the moment's preparation status), a prompt over its budget or a quote over the envelope (503 "Scene unavailable", not retryable, with an attention item). There is no fallback to the legacy engine or an unplanned prompt. Absent, stale or unloadable references are omitted and the packet records what was actually sent. After the provider attempt begins, a timeout, error or refusal releases the hold and fails the request; a duplicate or retried delivery replays the request record (202 while running, 200 with the saved image, 409 when it ended without one) and never starts a second paid attempt. Saved generic Bible images carry the WEB text with `translationId: "web"`, `engine: "generic"` and full provenance ([persistence](IMAGE-PERSISTENCE.md)); the reader's translation is kept as `requestTranslationId`.

The generic engine shares reservation, settlement, cost events and replay with the legacy path through the same Convex functions, so one ledger and one request identity serve both engines. The route's [generic engine tests](../../src/app/api/__tests__/generate-image/credit-flow.test.ts) exercise the real `POST` with controlled text and image providers: cold and warm success, preparation failure, optional-reference failure and staleness, over-budget prompts, refusal, missing usage, duplicate and concurrent delivery, an interrupted save, a timeout and the owner path. The five-credit Lite target has not yet been demonstrated with a paid production call; that evidence belongs to the release ticket.

Corrections to the generic engine's inputs (canon, looks, references, plans) and the attention list go through the [owner corrections runbook](../workflow/OWNER-CORRECTIONS.md); they never alter saved images or charges.
