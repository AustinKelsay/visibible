# Image generation

[POST /api/generate-image](../../src/app/api/generate-image/route.ts) performs the OpenRouter request in Next.js. Convex tracks state, credits and saved images; it is not a background worker for this request.

## Request lifecycle

1. Validate the origin, CSRF token, feature flag, OpenRouter key, signed session with current-IP tracking, rate limit and body.
2. Authenticated retries return the existing operation before catalog or Scripture reads. The request ID is claimed together with the session and a fingerprint of the immutable request fields; a retry with changed fields gets 409. This fingerprint also keys requests accepted by the removed legacy engine, so it must not change.
3. Resolve the required single-verse reference and selected translation through [the canonical passage resolver](../../src/lib/generation-passage.ts). The reference endpoint resolves aliases; a validated canonical chapter supplies the text. Client text, neighboring context and theme are compatibility fields only. Missing or invalid current text and upstream failures stop before reservation or provider work.
4. Decide the engine at admission ([Engine admission](#engine-admission)). Every new request runs on the generic engine ([Generic generation path](#generic-generation-path)); the legacy engine's code was removed from the route ([#184](https://github.com/AustinKelsay/visibible/issues/184)).

Lifecycle states are `queued`, `planning`, `generating`, `succeeded`, and `failed`. [verseImages.ts](../../convex/verseImages.ts) provides the lifecycle and storage functions; [schema.ts](../../convex/schema.ts) defines their fields. [costs.ts](../../convex/costs.ts) handles Neutral Cost and outbox replay.

## UI and pricing

[HeroImage](../../src/components/hero-image.tsx) sends a request ID, subscribes to lifecycle status, and registers generation controls with [GenerationContext](../../src/context/generation-context.tsx). Header controls share that state. First-image auto-generation requires loaded empty history and strict affordability; explicit actions can use the spend-down grace. Empty history alone does not cause a paid request.

`/api/image-models` supplies per-resolution catalog quotes and timing information. The quotes are the catalog price alone: the legacy scene planner's allowance went with the legacy engine (#184). The generic engine quotes its own prompt-aware price at admission. [Sessions and credits](SESSIONS_AND_CREDITS.md) explains holds, settlement and fallback charges.

## Configuration and related behavior

- `ENABLE_IMAGE_GENERATION=true` enables the route.
- The legacy scene planner and prompt builder were removed with the legacy engine (#184). So is their scene plan cache: its 20 production rows were exported to the [release record](../releases/2026-10-29-legacy-code-removal/README.md) and cleared, and the `scenePlanCache` table left the schema.
- [Prompt specification](../implementation/IMAGE_PROMPT_SPEC.md), [persistence](IMAGE-PERSISTENCE.md), and [bulk generation](BULK-GENERATION.md) cover those separate concerns.
- [Credit-flow](../../src/app/api/__tests__/generate-image/credit-flow.test.ts) tests cover request behavior.

Saved image records and replay responses preserve the original reference, translation and verse text; existing historical images are not rewritten.

## Catalog quotes and supported settings (T03)

[Image catalog](../../src/lib/image-catalog.ts) normalizes the general OpenRouter catalog for the existing chat-completion image request. It reads text input/output rates and `pricing.image_output` as USD per output token for the verified Gemini families; it never treats `pricing.image` as a generated-image price. Billing metadata contains its source, capture time, unit and policy version. Capabilities contain documentation provenance. The adapter does not switch generation APIs.

Generic reference images use the explicit `pricing.image` price when present. If it is absent for Gemini 3.1 Flash, Flash preview or Lite, the billing adapter uses Google's default 1,120 input tokens per reference at the catalog's unified text/image input rate. This is independent of output resolution. The policy version is `google-input-output-tokens-2026-10-20`; unknown input pricing and malformed explicit rates still refuse reference-bearing requests. [Google media token counts](https://ai.google.dev/gemini-api/docs/media-resolution), [pricing](https://ai.google.dev/gemini-api/docs/pricing) and [recorded provider usage](../releases/2026-10-20-disabled-engine/reference-pricing.md) support this normalization. Historical images and accepted request replays retain their original billing commitments.

Google documents 1,290 output tokens for Gemini 2.5 Flash Image. Gemini 3.1 Flash uses 1,120/1,680/2,520. Gemini 3.1 Flash Lite Image supports only 1K, at 1,120. Estimates additionally allow 1,000 text input and 1,000 text output tokens. These are estimation assumptions, not enforced spending caps. The combined decimal sum rounds to credits once. Sources: [Google image dimensions/token counts](https://ai.google.dev/gemini-api/docs/image-generation), [Google pricing](https://ai.google.dev/gemini-api/docs/pricing), [OpenRouter chat request contract](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request).

The verified registry covers the default, Gemini 3.1 Flash Lite Image; Gemini 2.5 Flash Image; and the Gemini 3.1 Flash stable and preview identifiers. The [image model comparison](../research/2026-10-14-image-models.md) explains the default and why Gemini 3 Pro was removed. The catalog leaves out models outside the registry until their output units and request settings are verified. Explicit unsupported settings fail before reservation/provider work. Stored resolutions normalize when selecting a model; a removed saved model requires an explicit new selection.

Discovery and admission use the same catalog quote. Cost samples are still recorded, but unversioned historical/model/provider/global estimates do not override current quotes. T05 introduces validated learned estimates. The model-list GET no longer starts a historical backfill.

A catalog outage may use a labeled last-known snapshot for at most six hours. Without one, choices are unavailable; the configured default is never inserted into a successful catalog that removed it. Selectors refetch when reopened. Scripture remains available during pricing failure.

Holds use the bounded headroom described in [Sessions and credits](SESSIONS_AND_CREDITS.md); final settlement still uses actual usage where available. A visible accepted maximum, input/output exposure bounds and versioned quote acceptance (T04) are not implemented. Historical charges are unchanged.

## Engine admission

Every new image request is bound to one engine at admission ([admission.ts](../../src/lib/engine/admission.ts)) and the binding is persisted on its `imageGenerationRequests` record (`engine`, `artStyleId`, and for the generic engine its `engineCommitments`: work, moment, brief version, analysis generation, prompt and billing versions). A replay of the same request returns the accepted engine and saved result and never reprices or switches engines; a request without an `engine` field is historical and legacy.

A request may name the engine it is bound to (`engine` in the body, sent by bulk jobs after their first accepted item); when admission would decide differently the route answers 409 "Engine binding changed" before any reservation or record, and the request id stays usable. Success and replay responses report `engine`. `GENERIC_ENGINE_MODE` selects the rollout stage: `disabled` (default) admits no new image and reports every style as temporarily unavailable with a retryable 503, leaving saved style preferences untouched (before #184 removed it, the legacy engine served Classical here); `owner` admits the generic engine only for a session whose tier is `admin`, verified server-side, so the owner can prove it in production; `public` sends every new request in a released style (`PUBLIC_GENERIC_STYLE_IDS` in [admission.ts](../../src/lib/engine/admission.ts): Classical, Watercolor and Fresco since the owner's 28 October decisions, and Storybook since the 1 November bake-off) to the generic engine, and keeps other styles (Icon) owner-only, reported as temporarily unavailable to readers. Generic admission also requires the work's analysis to be ready (`getWorkStatus`); when it is not, the request gets a retryable "Preparing scene" 503 rather than a legacy fallback. Optional references and open attention items never gate admission.

Generic dispatch goes through one seam ([dispatch.ts](../../src/lib/engine/dispatch.ts)) to the generic engine ([generation.ts](../../src/lib/engine/generation.ts)). The legacy engine is retired and its route code removed ([#184](https://github.com/AustinKelsay/visibible/issues/184)): admission only ever chooses the generic engine, so there is no new legacy admission, no legacy fallback for a refused Classical scene, and no new item for a job bound to legacy (409, or 503 while the generic engine is off), while accepted legacy requests still replay. The `LEGACY_ENGINE` switch that preceded the removal no longer exists. Rollback is `GENERIC_ENGINE_MODE=disabled`, which stops all new images while accepted requests of both engines replay; getting the legacy engine back needs a redeploy of a build from before the removal. The release, rollback and retirement steps, the rehearsal command and the evidence template are in the [engine release runbook](../workflow/ENGINE_RELEASE.md).

## Reader controls

The reader's art style ([Preferences](PREFERENCES.md)) goes with every request as `style`. `/api/image-models` reports `artStyles` with the same admission decision generation would make ([admission.ts](../../src/lib/engine/admission.ts)), so an offered style the server is not admitting is shown as temporarily unavailable, generation in it is disabled with a message, and saved images and the preference stay as they are; it is never silently replaced by Classical. While a non-Classical request has no request record yet the hero shows "Preparing scene…", and a retryable 503 (a scene still preparing, a style not admitted) is shown with the server's message and a retry. Variation numbers and auto-generation eligibility count only the selected style's images.

## Generic generation path

An admitted generic request runs, in order: the deployed work, brief and style files ([work-inputs.ts](../../src/lib/engine/work-inputs.ts), read once per instance and versioned like the owner scripts version them) must match the versions the active analysis was registered with, and the work's [depiction profile](WORK-PREPARATION.md#depiction-profile) is read beside them (versioned by content, never registered); the verse's moment and section come from the active analysis and the moment text and in-section neighbours from the imported reference text, never from the reader's translation; the section look and scene plan are prepared lazily and forgivingly, with each new plan reviewed, re-planned at most once and then kept with notes ([Scene preparation](SCENE-PREPARATION.md)); a missing assigned canon stage, unreadable planner replies, or a no-form subject still drawn as a body after the re-plan stops before a request record or guest reservation; the plan's present entries supply their exact canon stages, with section assignments and selected canon versions rechecked before reference loading; reference sheets and the style reference are used only when current for their entry, stage and style versions (or pinned) and when their bytes load, converted to JPEG and sent inline after the prompt; the rendering packet is built and validated ([prompt spec](../implementation/IMAGE_PROMPT_SPEC.md#generic-rendering-packet)); the prompt-aware quote is checked against the image envelope; affordability and the daily limit are checked; the request record is created with `engine: "generic"` and its commitments; the exact packet is persisted on the request (`renderingPacket`) before any paid attempt; credits are reserved (or the owner's audit entry written); one provider call is made; the finished image is checked for a figure in light (only in a work whose profile has subjects without form, in its wording), an unpainted edge (not counted for Watercolor, whose soft edges the owner accepts), a painted frame or lettering, and a faulty image gets one owner-funded retry, with the better of the two shown ([ADR 0007](../../docs/adr/0007-check-each-finished-image.md); `GENERIC_SCENE_CHECK=off` turns it off); settlement charges the reader for the image shown, and the cost event and the saved image keep the shape historical legacy images have. The checks and any unshown image are owner spend in the preparation ledger (`kind: "check"`).

Failures before the request record cost nothing and leave no request: inputs not deployed or mismatched, a missing moment, a look or plan that cannot be made (503 "Preparing scene", retryable, with the moment's preparation status), a prompt over its 12,000-character budget or a quote over the envelope (503 "Scene unavailable", not retryable, with an attention item). A refused scene keeps its 503 in every style: the Classical fallback to the legacy engine that [ADR 0004](../../docs/adr/0004-forgiving-scene-preparation.md) describes ended with the legacy engine (#184). A bulk job bound to legacy gets 409 for its next item and pauses. There is no unplanned generic prompt. Absent, stale or unloadable references are omitted and the packet records what was actually sent. After the provider attempt begins, a timeout, error or refusal releases the hold and fails the request; a duplicate or retried delivery replays the request record (202 while running, 200 with the saved image, 409 when it ended without one) and never starts a second paid attempt. Saved generic Bible images carry the WEB text with `translationId: "web"`, `engine: "generic"` and full provenance ([persistence](IMAGE-PERSISTENCE.md)); the reader's translation is kept as `requestTranslationId`.

Accepted legacy requests replay through the same Convex functions the generic engine uses, so one ledger and one request identity serve both engines' records. The route's [generic engine tests](../../src/app/api/__tests__/generate-image/credit-flow.test.ts) exercise the real `POST` with controlled text and image providers: cold and warm success, preparation failure, optional-reference failure and staleness, over-budget prompts, refusal, provider errors, missing usage, credit and daily-limit refusals, admission failure, changed input, duplicate and concurrent delivery, an interrupted save, a timeout, the owner path and the replay of an accepted legacy request. The five-credit Lite target has not yet been demonstrated with a paid production call; that evidence belongs to the release ticket.

Corrections to the generic engine's inputs (canon, looks, references, plans) and the attention list go through the [owner corrections runbook](../workflow/OWNER-CORRECTIONS.md); they never alter saved images or charges.
