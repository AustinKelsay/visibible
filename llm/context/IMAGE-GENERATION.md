# Image generation

[POST /api/generate-image](../../src/app/api/generate-image/route.ts) performs the OpenRouter request in Next.js. Convex tracks state, credits and saved images; it is not a background worker for this request.

## Request lifecycle

1. Validate the origin, CSRF token, feature flag, OpenRouter key, signed session with current-IP tracking, rate limit and body.
2. Authenticated retries return the existing operation before catalog or Scripture reads. The request ID is claimed together with the session and a fingerprint of the immutable request fields; a retry with changed fields gets 409. This fingerprint also keys requests accepted by the removed legacy engine, so it must not change.
3. Resolve the required single-verse reference and selected translation through [the canonical passage resolver](../../src/lib/generation-passage.ts). The reference endpoint resolves aliases; a validated canonical chapter supplies the text (for WEB, the imported chapter when the service's is unusable: [Bible API](BIBLE-API.md#default-translation-imported-text-as-stand-in)). Client text, neighboring context and theme are compatibility fields only. Missing or invalid current text and upstream failures stop before reservation or provider work. A prose request instead names `workId` and `unitId` (a moment's first unit) from the [catalog](../../src/lib/works/catalog.ts). The unit and its reference come from the work's imported text, with no Bible lookup, and that work's readiness admits it. A work still in the owner's preview answers anyone but an admin session with the same 404 as an unknown work, before the passage is checked. The unit must begin one of the active generation's moments, since images are saved under it and the reader looks there. Bible fingerprints are unchanged; only prose requests add the work and unit to theirs.
4. Decide the engine at admission ([Engine admission](#engine-admission)). Every new request runs on the generic engine ([Generic generation path](#generic-generation-path)).

Lifecycle states are `queued`, `generating`, `succeeded`, and `failed`. `planning` remains valid on older records; new requests never enter it. [verseImages.ts](../../convex/verseImages.ts) provides the lifecycle and storage functions; [schema.ts](../../convex/schema.ts) defines their fields. [costs.ts](../../convex/costs.ts) handles Neutral Cost and outbox replay.

## UI and pricing

[HeroImage](../../src/components/hero-image.tsx) sends a request ID, subscribes to lifecycle status, and registers generation controls with [GenerationContext](../../src/context/generation-context.tsx). Header controls share that state. First-image auto-generation requires loaded empty history, strict affordability and, for a guest, the `autoGenerate` preference they turned on themselves ([Preferences](PREFERENCES.md)); the owner is not charged and needs no preference. It is sent as `automatic`; explicit actions can use the spend-down grace. Empty history alone does not cause a paid request.

The single-generation controls show the server's quote for the image as it would be generated now, as "About N credits · at most M": the header's Generate button, the Generate button in its dialog, the selected model's line there, and the Generate button on an empty stage. HeroImage reads the quote from `POST /api/generate-image/quote` for a guest with credits, 400 ms after the moment and settings settle, and again when a setting or the balance changes and after each attempt. Until it is read the controls show no number. A click sends the quote's id. When the server answers `Quote stale`, a fresh quote at the price just accepted (the old one had only expired) is accepted for the guest once; at any other price, or when no price was on screen, the stage and the dialog show it and wait for "Generate at this price". The owner is not quoted.

`/api/image-models` supplies per-resolution catalog estimates and timing information: the catalog price alone, used for the model and resolution lists, the bulk estimate and the credit-pack sizing, and to decide whether Generate is offered at all. It is not what a guest is charged. [Sessions and credits](SESSIONS_AND_CREDITS.md#quotes-and-the-maximum-charge) explains quotes, holds, settlement and fallback charges.

## Catalog quotes and supported settings (T03)

[Image catalog](../../src/lib/image-catalog.ts) normalizes the general OpenRouter catalog for the existing chat-completion image request. It reads text input/output rates and `pricing.image_output` as USD per output token for the verified Gemini families; it never treats `pricing.image` as a generated-image price. Billing metadata contains its source, capture time, unit and policy version. Capabilities contain documentation provenance. The adapter does not switch generation APIs.

Generic reference images use the explicit `pricing.image` price when present. If it is absent for Gemini 3.1 Flash, Flash preview or Lite, the billing adapter uses Google's default 1,120 input tokens per reference at the catalog's unified text/image input rate. This is independent of output resolution. The policy version is `google-input-output-tokens-2026-10-20`; unknown input pricing and malformed explicit rates still refuse reference-bearing requests. [Google media token counts](https://ai.google.dev/gemini-api/docs/media-resolution), [pricing](https://ai.google.dev/gemini-api/docs/pricing) and [recorded provider usage](../releases/2026-10-20-disabled-engine/reference-pricing.md) support this normalization. Historical images and accepted request replays retain their original billing commitments.

Google documents 1,290 output tokens for Gemini 2.5 Flash Image. Gemini 3.1 Flash uses 1,120/1,680/2,520. Gemini 3.1 Flash Lite Image supports only 1K, at 1,120. Nano Banana 2.1 measured 1,120 at 1K and 1,120 input tokens per reference over 254 calls; its larger sizes are unverified and not offered. It also bills about 600 reasoning tokens with each image, which the generic quote allows for. Estimates additionally allow 1,000 text input and 1,000 text output tokens. These are estimation assumptions, not enforced spending caps. The combined decimal sum rounds to credits once. Sources: [Google image dimensions/token counts](https://ai.google.dev/gemini-api/docs/image-generation), [Google pricing](https://ai.google.dev/gemini-api/docs/pricing), [OpenRouter chat request contract](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request).

The verified registry covers the default, Nano Banana 2.1 (since [ADR 0012](../../docs/adr/0012-one-image-call-from-the-text.md)); Gemini 3.1 Flash Lite Image; Gemini 2.5 Flash Image; and the Gemini 3.1 Flash stable and preview identifiers. The [image model comparison](../research/2026-10-14-image-models.md) explains the default and why Gemini 3 Pro was removed. The catalog leaves out models outside the registry until their output units and request settings are verified. Explicit unsupported settings fail before reservation/provider work. `/api/image-models` offers only the default, since the engine generates on it whatever model a request names; a saved preference for another model is reset on load ([Preferences](PREFERENCES.md)).

Discovery and admission use the same catalog quote. The model-list GET starts no historical backfill.

A catalog outage may use a labeled last-known snapshot for at most six hours. Without one, choices are unavailable; the configured default is never inserted into a successful catalog that removed it. Selectors refetch when reopened. Scripture remains available during pricing failure.

A request holds the maximum of its accepted quote, and settlement uses actual usage, never above that maximum ([Sessions and credits](SESSIONS_AND_CREDITS.md#quotes-and-the-maximum-charge)). Historical charges are unchanged.

## Engine admission

Every new image request is bound to one engine at admission ([admission.ts](../../src/lib/engine/admission.ts)) and the binding is persisted on its `imageGenerationRequests` record (`engine`, `artStyleId`, and for the generic engine its `engineCommitments`: work, moment, brief version, analysis generation, prompt and billing versions). A replay of the same request returns the accepted engine and saved result and never reprices or switches engines; a request without an `engine` field is historical and legacy.

A request may name the engine it is bound to (`engine` in the body, sent by bulk jobs after their first accepted item); when admission would decide differently the route answers 409 "Engine binding changed" before any reservation or record, and the request id stays usable. Success and replay responses report `engine`. `GENERIC_ENGINE_MODE` decides who is admitted once `ENABLE_IMAGE_GENERATION` is on: `public` (the default when unset) admits every reader in a released style; `owner` admits only owner sessions, in any style; `disabled`, or any unrecognised value, admits no new image and reports every style as temporarily unavailable with a retryable 503, leaving saved style preferences untouched. Owner status is verified server-side from the session's tier; owners also reach owner-only styles such as Icon in public mode. See the [release runbook](../workflow/ENGINE_RELEASE.md#engine-modes). Generic admission also requires the work's analysis to be ready (`getWorkStatus`); when it is not, the request gets a retryable "Preparing scene" 503 rather than a legacy fallback. Optional references and open attention items never gate admission.

Generic dispatch goes through one seam ([dispatch.ts](../../src/lib/engine/dispatch.ts)) to the generic engine ([generation.ts](../../src/lib/engine/generation.ts)). Admission only ever chooses the generic engine: there is no legacy admission or fallback, a job bound to legacy gets no new item (409, or 503 while the generic engine is off), and accepted legacy requests still replay. To stop new images set `GENERIC_ENGINE_MODE=disabled`; accepted requests still replay ([release runbook](../workflow/ENGINE_RELEASE.md#rollback)).

## Reader controls

The reader's art style ([Preferences](PREFERENCES.md)) goes with every request as `style`. `/api/image-models` reports `artStyles` with the same admission decision generation would make. With `?work=<prose work>` it reads that work's readiness, marks styles outside its brief unavailable, and answers as for the Bible when the viewer may not open the work ([admission.ts](../../src/lib/engine/admission.ts)), so an offered style the server is not admitting is shown as temporarily unavailable, generation in it is disabled with a message, and saved images and the preference stay as they are; it is never silently replaced by Classical. While a non-Classical request has no request record yet the hero shows "Preparing scene…", and a retryable 503 (a work not ready, a style not admitted) is shown with the server's message and a retry. Variation numbers and auto-generation eligibility count only the selected style's images.

## Generic generation path

An admitted generic request makes one paid call ([ADR 0012](../../docs/adr/0012-one-image-call-from-the-text.md)). In order:

1. **Inputs.** The deployed work, brief and style files ([work-inputs.ts](../../src/lib/engine/work-inputs.ts), read once per instance) must match the versions the active analysis was registered with. The work's [depiction profile](WORK-PREPARATION.md#depiction-profile) is read beside them.
2. **Assembly** ([lean-assemble.ts](../../src/lib/engine/lean-assemble.ts)). The verse's moment and section come from the active analysis; the moment text and in-section neighbours come from the imported reference text, never the reader's translation. Every member of the section's cast is read with the canon stage the section assigns. A member whose canon cannot be read stops the image before any charge, because it may be a subject without form.
3. **References.** The style reference and up to four sheets are used only when current for their entry, stage and style versions (or pinned) and when their bytes load. They are converted to JPEG and sent inline after the prompt.
4. **Prompt** ([lean.ts](../../src/lib/engine/lean.ts)). One prompt is built from the text itself: the rules, the moment and its neighbours, the brief, the section's places as the setting, the cast's canon (members the text names first) and the art style. No model plans the scene. A subject without form is renamed everywhere and described by its work's wording.
5. **Quote and admission.** The prompt-aware quote is checked against the image envelope, then affordability and the daily limit. A quote request (`POST /api/generate-image/quote`) stops here and returns the estimate, maximum, expiry and quote id. A generation must present the quote the guest accepted: its terms are recomputed from this prompt, these settings, the catalog price and the balance, and a quote that is missing, used, expired, another session's or issued for other terms is answered with 409 `Quote stale` and a fresh quote. Automatic generation has its quote issued and accepted here instead, and the owner needs none. Only then is the request record created, with `engine: "generic"`, its commitments, the quote id and the maximum, and the exact packet persisted (`renderingPacket`) before any paid attempt.
6. **The image.** Exactly the accepted maximum is reserved (or the owner's audit entry written) and one provider call is made on Nano Banana 2.1. The image is shown as made: there is no finished-image check and no retry.
7. **Settlement.** The reader is charged from actual usage, capped at the accepted maximum (`chargeCapped` in the response when it applied), or the accepted estimate when the provider reports none. The cost event and the saved image keep the shape historical images have.

Failures before the request record cost nothing and leave no request: inputs not deployed or mismatched, a missing moment, or a cast member without canon (503 "Preparing scene", retryable); a prompt over its 12,000-character budget or a quote over the envelope (503 "Scene unavailable", not retryable, with an attention item); a stale quote (409 `Quote stale`, with a fresh quote). A bulk job bound to legacy gets 409 for its next item and pauses. Absent, stale or unloadable references are omitted and the packet records what was actually sent. After the provider attempt begins, a timeout, error or refusal releases the hold and fails the request; a duplicate or retried delivery replays the request record (202 while running, 200 with the saved image, 409 when it ended without one) and never starts a second paid attempt. Saved generic Bible images carry the WEB text with `translationId: "web"`, `engine: "generic"` and full provenance ([persistence](IMAGE-PERSISTENCE.md)); the reader's translation is kept as `requestTranslationId`.

Accepted legacy requests replay through the same Convex functions the generic engine uses, so one ledger and one request identity serve both engines' records. The route's [generic engine tests](../../src/app/api/__tests__/generate-image/credit-flow.test.ts) exercise the real `POST` with a controlled image provider: success in two styles, optional-reference failure and staleness, missing canon, over-budget prompts, refusal, provider errors, missing usage, credit and daily-limit refusals, admission failure, changed input, duplicate and concurrent delivery, an interrupted save, a timeout, the owner path and the replay of an accepted legacy request. Most run as automatic generation; the quote protocol has its own group there (quote, accept, hold and finish; provider failure and release; expiry; a tampered or other-session id; a changed catalog price or setting; the grace; a capped charge; missing usage; reuse).

Corrections to the generic engine's inputs (canon and references) and the attention list go through the [owner corrections runbook](../workflow/OWNER-CORRECTIONS.md); they never alter saved images or charges.
