# Saved images

[The image route](../../src/app/api/generate-image/route.ts) calls server-secret-protected `saveImage` in [verseImages.ts](../../convex/verseImages.ts). Browser components query history; they do not call this write action directly.

Verse IDs group history by reference (for example `genesis-1-1`), without translation. Records retain translation and generation metadata, so shared history may include multiple translations. [HeroImage](../../src/components/hero-image.tsx) defaults to the latest image and supports older/newer selection; [Navigation](NAVIGATION.md) describes the spread and Contents.

## Storage and fallback

- `saveImage` stores only image bytes returned with the provider response (a data URL). The data must be standard base64 (padding only at the end, or omitted), of a declared PNG, JPEG, WebP or GIF type, and at most 10 MiB. The bytes must be a whole image of that type: its dimensions read, and its structure complete to the end (PNG with a nonempty IDAT stream through IEND, JPEG walked segment by segment through its scans to the end marker, GIF through the trailer, WebP with an encoded VP8 or VP8L image filling its RIFF size exactly). Malformed base64, non-image, mislabelled, truncated and oversize data are refused and nothing is saved. When a response names both bytes and a remote URL, the engine takes the bytes ([image-response.ts](../../src/lib/image-response.ts)).
- A remote image URL is refused without being fetched. Convex's runtime cannot resolve a URL's destination, so a fetch could not be kept off private or DNS-rebound addresses, and the 80 most recent production images, back to April 2026, all arrived as data. Remote fetching, the host allowlist (`IMAGE_FETCH_ALLOWLIST`, now unread) and the URL-backed fallback record were removed on 10 November 2026 (#80). Older URL-backed records still read as before.
- A refused or failed save throws; it never creates a record. The image route logs it and still answers with the image, without a `savedImageId`; a generation can therefore succeed in the browser without a durable stored image (#81).

[convex/http.ts](../../convex/http.ts) serves stored bytes at `/image/:storageId`. Image link construction uses `NOSTR_IMAGE_BASE_URL`, then `CONVEX_SITE_URL`, then `CONVEX_CLOUD_URL`; configure a base that actually serves that HTTP route. Storage rows can be reused across browser sessions within the same deployment.

[Public API](PUBLIC-IMAGE-API.md) describes the reduced external response, which intentionally omits prompts and cost details. [Nostr](NOSTR.md) describes scheduled sharing.

The engine's analysis (sections, moments, canon and references) lives in separate tables described in [Analysis storage](ANALYSIS-STORAGE.md); saved image records are not changed by analysis activations or owner corrections.

Reference sheets and style references for the generic engine are image blobs in the same file storage, written by the `storeReferenceBlob` action in the format the model returned and recorded in `referenceImages` with their input versions ([Reference images](WORK-PREPARATION.md#reference-images)). At request time the engine reads them through the server-only `getReferenceBlobUrl` query, converts them to JPEG with sharp, and keeps the JPEG bytes in a bounded per-instance cache (`createReferenceBlobCache`) before sending them inline; they are never fetched from a browser.

## Thumbnails

Each saved picture can have a small copy, `thumbnailStorageId`, so walls of pictures and previews do not download full paintings (#444).

- New pictures: the generic engine makes the copy in the request that saves the picture, after settlement ([generation.ts](../../src/lib/engine/generation.ts) with [thumbnails.ts](../../src/lib/thumbnails.ts)): a WebP whose shorter side is at most 384 pixels, never enlarged, at quality 70. It is sent to `saveImage` as `thumbnailUrl`, a data URL checked like the picture (whole image, allowed type) but capped at 512 KiB, and stored beside the picture in the same action. Making, checking or storing it can fail (a five-second limit applies to making it): the failure is logged, the picture is saved without a thumbnail, and the charge is unchanged because it is settled before the save. When saves of one generation race, the losing upload's thumbnail is deleted with its picture.
- Resizing runs in the Next.js server with sharp, which the engine already loads for reference sheets. sharp 0.35 ships prebuilt binaries as optional platform packages and has no install script, so it works with the repository's `ignore-scripts`. Convex's default runtime cannot run it, and no image-resizing service is used.
- Reads: `getImageHistory`, `getChapterContents` (the tile picture) and the replay of a finished request (`savedImage`, and the image route's replay response) return `thumbnailUrl`, a storage address, or `null` when the picture has none. Readers then use the full picture; [picture-source.ts](../../src/lib/picture-source.ts) `previewSource` picks one. The public image API does not return thumbnails, and its responses are unchanged.
- Existing pictures: the owner runs the one-time backfill, against development first and against production at cutover, before the new reader ships:

  ```bash
  CONVEX_SERVER_SECRET=… npm run thumbnails:backfill -- --convex-url <deployment URL> --dry-run
  CONVEX_SERVER_SECRET=… npm run thumbnails:backfill -- --convex-url <deployment URL> [--limit <pictures>]
  ```

  [The script](../../scripts/thumbnails/backfill.mts) pages through the server-only `listPicturesWithoutThumbnail` query (the `by_thumbnailStorageId` index, oldest first), downloads each picture from its storage address, makes the thumbnail locally and sends it to the server-only `attachThumbnail` action. A dry run lists what it would do and changes nothing. A run is resumable and safe to repeat: it reads only pictures still without a thumbnail, `attachThumbnail` keeps a thumbnail a picture already has (and deletes a copy that lost a race), and Ctrl-C stops after the picture in hand. A picture it cannot read is reported in the final JSON report and retried by the next run.

## Art style at read time

Images rendered by the generic engine store `artStyleId`; historical images have none and every library read ([verseImages.ts](../../convex/verseImages.ts)) reports them as `classical` through `artStyleOf`. The style-aware queries (`getImageHistory`, `getChapterImageStatus`, `getBooksWithImages`, `getChaptersWithImages` and the public queries) take an optional `artStyle`, and the browser queries also `otherStyles: true` for an "other styles" view; the filter runs inside the database read so history, counts, markers, existence checks and pages agree. Book and chapter existence checks for one style read the style-leading `by_artStyle_verse` index (Classical also checks images with no stored style); the "other styles" form has no bounded index and scans the range. Omitting the style preserves the previous all-styles behavior. `getChapterContents` instead takes an ordered list of styles and returns each verse's newest picture in the first style that has one, read from the `by_verse_artStyle` index ([Navigation](NAVIGATION.md)). `getNearestEarlierPicture({ verseId, artStyle })` answers the spread's glow behind an unpainted verse: the newest visible picture in the style of the nearest earlier verse of the same chapter, with `thumbnailUrl`, or `null`. It reads one exact verse id per earlier verse, stopping at the first hit, so it never scans the chapter. Each record also reports `engine` and `requestTranslationId` (the reader's translation at request time) beside the saved `translationId`, which names the image's own source text.

## Generic-engine provenance

Images saved by the generic engine carry `engine: "generic"` and a `provenance` object: work, moment, section and era, the art style and its file version, the brief version, the prompt version, the work's depiction profile version (from 30 October 2026; earlier images have none), the analysis generation, the selected canon stages with their versions, and the references actually sent with their versions, plus `requestTranslationId`, the reader's selected translation at request time. Images saved before 10 November 2026 also carry `lookVersion` and `planVersion`, the full engine's versions or `none` from the first lean images; newer images omit both ([ADR 0012](../../docs/adr/0012-one-image-call-from-the-text.md)). Their `verseText` is the work's reference text and their `translationId` names it (`web` for the Bible). Both fields are optional: historical images have neither, their source stays unknown, and nothing rewrites them. The accepted request keeps the full `renderingPacket` snapshot, persisted before the provider attempt, so an image can be explained from its request as well as its record.
