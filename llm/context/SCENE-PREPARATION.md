# Section looks and scene plans

[Lazy preparation](../../src/lib/engine/preparation.ts) makes the two pieces of text the generic engine needs before it can draw a moment, the first time they are needed, and stores them in the work's active analysis generation ([Analysis storage](ANALYSIS-STORAGE.md)). The legacy route's scene planner and its `scenePlanCache` are untouched and separate.

- **Section look**: one per story section, shared by every image of that section in every art style and reader translation. It holds the situational place, time of day, weather, light and clothing, and never restates canon. Its inputs are the section version, the brief version and the canon versions of the section's cast.
- **Scene plan**: one per moment, shared by every art style and reader translation. Claude Haiku 5.5 sees the moment's reference text, its neighbours inside the same section (a section boundary gives none), the brief and era, the section look and the section's cast, and returns which cast are present plus subject, action, setting, secondary elements, mood, time and composition. Code pairs each present entry with the stage the section assigns it; if that stage ID is missing, preparation and rendering fall back to the entry's first stage. Inputs: the moment, look, brief and the cast's canon versions, plus the presence-prompt version when the cast includes a no-form entry. Nothing about a style or a translation enters the plan or its identity, so rendering-only changes never create per-style copies.

**Presence without a body.** For sections whose cast includes `hasForm: false`, the planner receives each cast member's `hasForm` flag and the assigned canon stage text of the no-form entries. These fixed descriptions are planning constraints, not scene-plan fields; formed entries' canon text is not added to the planner request. Instructions require the permitted visible effects and their placement rather than bodily poses, silhouettes, clothing or negated substitutes such as a faceless figure. Bodily source metaphors about a no-form subject do not grant a physical form: a seated metaphor becomes an unoccupied seat with the permitted surrounding effects. Formed characters retain their own poses, clothing and actions. The source quotation is unchanged.

The planner must still include a no-form entry in `present` when describing its presence or action and select only the cast present in this moment; code does not append the whole section cast. Missing legacy flags mean `true`, consistently with rendering and reference selection. Selected no-form entries supply their assigned canon stage and the rendering packet's protected depiction constraints, but never a sheet. Absent entries supply neither canon nor references to the rendering packet, even though their canon was available as section context to the planner.

Affected requests use a strict response schema that restricts `present` to the known section cast IDs. Local validation enforces the existing 220-character limit on each of the seven scene fields. [Anthropic does not support `maxLength` in raw output schemas](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations), so each field describes its limit while a Zod refinement checks it locally without serializing that unsupported keyword. An empty `present` array is allowed; the schema does not force any cast into a moment. Descriptions on the response fields guide the model toward visible effects, placement and formed characters' actions, consistent with the same system instructions and supplied canon. An unknown cast ID or overlong field is an invalid response, handled by the existing single schema/error retry. After two invalid attempts, preparation fails before reference loading or any image call; code does not silently filter IDs or truncate fields on these affected requests.

These affected plans add an input with kind `prompt`, id `scene_plan_formless_presence` and version `2026-10-21-formless-presence-v3`. A missing or older marker, including v1 and v2, makes the plan refresh lazily on next use, preserving prior records in history and reusing an unchanged look. It does not immediately regenerate stored plans. Sections whose cast all have form keep their previous planner request, response schema, unknown-ID filtering and cache identity. Once this code is deployed, affected cache misses incur ordinary owner-funded planning calls; this change adds no sweep or deployment.

The [offline presence regressions](../../src/lib/__tests__/engine-presence.test.ts) exercise real analysis storage through rendering assembly across all three styles, the serialized provider schema, field-length boundaries, rejected cast IDs, retry spend and successful retry reuse, assigned stages and their first-stage fallback after owner correction, missing/older prompt versions, absent no-form cast and legacy formed entries. Scripted replies prove the structural validation and request/selection/cache plumbing, not model obedience. A schema-valid contradictory reply is still stored verbatim and reaches rendering alongside protected canon; there is no semantic validator, silent rewrite or extra semantic retry. The [retained Daniel retest](../releases/2026-10-21-daniel-presence-retest/README.md) restored presence selection but left five failed and one ambiguous no-form image. The offline regressions do not establish corrected live behavior or release acceptance; those remain evaluation gates.

The subsequent [live v2 planning pilot](../releases/2026-10-21-daniel-canon-pilot/README.md) made one normal lazy plan call and stopped before images. The response selected both subjects and received the assigned no-form canon, but repeated prohibited face/body denials and left throne occupancy ambiguous. An agent review rejected that wording without editing or selectively retrying the stored plan. Its IDs and field lengths satisfy the v3 structural constraints; field descriptions are additional model guidance and do not reject this semantic failure. Three read-only packets are retained as unsent inputs; no image-quality improvement or release acceptance is established.

`prepareMoment` returns the look, the plan, the present entries with their stages and canon versions, and the number of calls it made. A record whose stored inputs no longer match the current versions is remade; an owner version is never overwritten, since a remake writes a new generated version only where the owner's inputs changed, and `clearRecord` on a plan simply forces a future replan. Saved images are never touched.

**Concurrency.** Two requests missing the same record take a claim in Convex (`claimPreparation`); the holder funds the call and releases the claim, the others poll for the record for up to 45 s and otherwise return a retryable error. Within one server instance the same promise is shared. `getPreparationStatus` reports `missing`, `preparing` or `ready` for a moment's look and plan so the reader can see "Preparing scene".

**Failure.** A model error or invalid JSON is retried once; then `PreparationUnavailableError` (retryable) is raised before any image call. There is no unplanned prompt and no legacy fallback. Every attempt, successful or not, is written to `preparationLedger` as owner spend (`getPreparationSpend`); no guest credit is reserved or charged for preparation.

**In the request path.** The generic engine ([generation.ts](../../src/lib/engine/generation.ts)) calls `prepareMoment` after resolving the verse's moment from the deployed work and before building the rendering packet; its "Preparing scene" 503 carries `getPreparationStatus` for that moment so the reader can be told whether the look or plan is missing or being made. See [Image generation](IMAGE-GENERATION.md#generic-generation-path).
