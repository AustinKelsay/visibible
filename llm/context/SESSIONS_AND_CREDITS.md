# Sessions and credits

[session.ts](../../src/lib/session.ts) signs the `visibible_session` JWT cookie and verifies session expiry. IP changes are logged and rotate the cookie; they do not invalidate the session by themselves. Session records and balances live in [convex/sessions.ts](../../convex/sessions.ts), not in browser storage. The browser cookie provides access to that anonymous session; clearing it or changing browsers does not transfer the balance.

New sessions are `paid` tier with zero credits. Admin tier bypasses credit/spending checks and lasts seven days from each admin login (`adminUntil`, `ADMIN_WINDOW_MS` in [sessions.ts](../../convex/sessions.ts)); a job every 15 minutes returns a session past its window, or an admin session with no window, to `paid` without touching its balance. Admin usage is audited. Admins still pass the routes' rate limits. Default expiry is 60 days idle with a 365-day absolute cap; activity refreshes are bounded by that cap. These were seven and thirty days until 14 November 2026, when they were lengthened because the session is a guest's only key to prepaid credits; the idle limit stays under the 90 days a stored session record lasts, and the admin window keeps owner access short. Timeout overrides and valid ranges are in [.env.example](../../.env.example).

## Reservation and settlement

Credits are reserved atomically before paid generation. Each generation ID has a one-way settlement: reserved → charged or released. Duplicate terminal operations must not create another charge/refund, and released IDs cannot be reserved again. Crons reconcile stale reservation-only generations after thirty minutes; [crons.ts](../../convex/crons.ts) is the schedule source.

- **Chat:** one turn holds its accepted maximum and is charged only for a successful model outcome, from the tokens the provider reports, never above that maximum; [Chat](CHAT.md) defines success and the reported settlement metadata. Errors, empty output and cancellation release the whole hold.
- **Images:** the engine quotes the actual assembled prompt and every reference image sent ([prompt spec](../implementation/IMAGE_PROMPT_SPEC.md#quotes)). The hold is the accepted maximum, and a successful image is charged from reported usage, never above that maximum; the rest of the hold returns. A refused quote (over the envelope) costs the guest nothing and records no request. Reading, canon and sheets are owner spend made ahead of time and never enter a guest's quote.

## Quotes and the maximum charge

Since #60, paid work starts from a quote: an estimate and a maximum charge that the guest sees and accepts, stored in the Convex `quotes` table ([convex/quotes.ts](../../convex/quotes.ts)). A quote records its session, its operation (image or chat), a fingerprint of everything that determines the price, the policy version, both amounts and an expiry five minutes after it was issued. The quote id is the document id. One operation accepts a quote, once.

| | Estimate | Maximum |
| --- | --- | --- |
| Image | The prompt-aware quote | Twice the quote (`IMAGE_RESERVATION_HEADROOM_MULTIPLIER`), and never more than the guest's balance |
| Chat turn | A typical turn: 1,000 tokens in and 1,000 out at the model's prices | The most the server sends and accepts back: 8,000 tokens in (6,000 of history and a 2,000-token system prompt allowance) and the output cap (2,048, less for a small context window) |

[quotes.ts](../../src/lib/quotes.ts) computes these terms and the fingerprint. An image's fingerprint covers the work, unit, reference, translation, style, model, aspect ratio, resolution, a hash of the assembled prompt, the number of reference images sent, the catalog billing version and the catalog rates themselves (a rate can move without the rounded credits moving, and the quote is refused all the same). A chat turn's covers the model, both token prices and the two token bounds. The estimate is never above the maximum.

The protocol is the same for both operations:

1. **Quote.** `POST /api/generate-image/quote` runs the same checks, admission and assembly as generation and stops at the quote; `POST /api/chat/quote` prices the selected model. Neither calls a model or holds credits. Each has its own rate limit (`image-quote`, `chat-quote`). The owner, who is not charged, gets `{ quote: null }`.
2. **Accept.** The paid request carries `quoteId`. The server recomputes the terms from the request it is about to make and accepts the quote only if it exists, belongs to the session, is unused and unexpired, and was issued for the same fingerprint, policy version, estimate and maximum. The same request presenting its quote again (a retry) is checked against the stored terms too, so an acceptance is never honoured at another price. Otherwise it answers 409 `Quote stale` with a `reason` (`missing`, `used`, `expired` or `changed`) and a fresh `quote`, before any request record, hold or model call. A missing, tampered or other-session id all read as `missing`.
3. **Hold.** Exactly the accepted maximum is reserved, once.
4. **Settle.** The charge is actual usage capped at the accepted maximum. When the provider reports no usage, the charge is the accepted estimate and the record says so (`usedFallbackEstimate` on the image request and its cost event; on the quote for a chat turn, with `chargedCredits`). A chat turn counts as reported only when both token counts arrive; a reported zero is a count, and half a report is treated as none. An image whose provider cost is reported as zero is likewise known usage and settles at the one-credit minimum. Provider spend above the maximum is absorbed by Visibible and logged (`settlement.event` with outcome `capped`); the image cost event keeps `openRouterUsageUsd` beside the capped charge. The session's daily spending limit still counts the work's full cost, not the capped charge, so work above the cap is not free of that limit.

A failure after acceptance releases the whole hold and leaves the quote used, so a retry needs a new quote. A repeated delivery of the same image request id is a replay, not a second use.

Operations admitted this way record `billingPolicyVersion: "accepted-maximum-v1"`, with `quoteId` and `maximumCreditsCost` on the image request. Earlier requests keep `legacy-image-v1` and are neither repriced nor capped. Quotes that expire unaccepted are deleted hourly; accepted quotes are kept as the record of what was authorized.

**Spend-down grace and automatic generation.** A guest with a positive balance up to five credits short of an image's estimate may still run an explicit image ([image-models.ts](../../src/lib/image-models.ts)); the estimate, the hold and the maximum are then capped to the balance, so the image takes at most what the guest has. A guest gets a first-visit image only after turning on "Generate automatically" in the image settings (`autoGenerate` in [Preferences](PREFERENCES.md), off by default since 14 November 2026); the owner, who is not charged, always does. Automatic generation (the first-visit image and bulk items) has no guest to accept a quote: the request is marked `automatic`, the server issues and accepts the quote itself (`origin: "automatic"`), and the whole estimate must be affordable. A chat turn has no grace: its whole maximum must be affordable. [chat-models.ts](../../src/lib/chat-models.ts) defines chat pricing.

Chat refuses a model whose estimate passes 100 credits. The image route refuses a quote over its ten-credit envelope instead. Convex applies non-admin daily spending checks to the held maximum (default $5/day, reset at UTC midnight). A guest's charge cannot pass the maximum they accepted; the provider's cost to Visibible still can, since token bounds are estimates. Read the route checks and Convex settlement together when changing pricing.

[SessionProvider](../../src/context/session-context.tsx) subscribes to authenticated `guestAuth.current` for available credits, pending holds and current tier. The outer guest provider bootstraps cookie identity and owns purchase-modal state. Single-image, bulk and purchase callers no longer subtract balances locally or refetch them after work. Loading, unavailable access and a verified zero balance have distinct displays. Holds are already deducted from available credits. See [wallet rollout and backfill](../../docs/agents/guest-auth.md#reactive-wallet-rollout). Without Convex, free browsing remains available but session-backed AI generation/billing is unavailable. See [Payments](PAYMENTS.md), [Security](SECURITY.md), and [Image generation](IMAGE-GENERATION.md).

Chat catalog rates, including emergency fallback rates, are USD per token. [Token pricing](../../src/lib/token-pricing.ts) validates rates and token counts, sums decimal amounts exactly and rounds credits once after markup. Invalid or missing pricing returns no quote; known zero provider spend remains distinct. The existing one-credit minimum is retained. This changes new estimates and metadata only; historical ledger entries are not repriced.

Access expiry is separate from record retention. Cleanup preserves funded sessions and sessions linked to any ledger, invoice, bulk job or image generation record. Only expired, empty, unlinked sessions are deleted, in bounded cursor batches. Operators can run a dry run first. Retention does not restore expired-cookie access or add cross-device recovery.

Lightning purchase settlement, including late payment after local expiry, is described in [Payments](PAYMENTS.md).

Daily-limit reconciliation is associated with the reservation's admission day. A previous day's release, cleanup, or settlement cannot subtract from or add to a newer session daily bucket. Before the next admission resets that bucket, the original day's adjustment still applies. Reservation retries return the existing hold before evaluating remaining daily allowance. Daily tracking counts the held maximum at admission and the work's full cost at settlement. When a charge is capped at the accepted maximum, the daily total still counts what the work cost, so the next admission check sees it.
