# Image eval and release requirements

Apply this process when changing the image prompt, an art style, the default image model, or anything else that can change what a verse's image looks like. It is the image half of [Spec S10](https://github.com/AustinKelsay/visibible/issues/54); the chat half is [Chat eval and release requirements](CHAT_EVAL_AND_RELEASE.md).

## The regression suite

Every measurement of the engine runs over the regression suite's cases ([ADR 0011](../../docs/adr/0011-frozen-multi-work-regression-suite.md)): the Bible, Holmes and Alice, a holdout nobody tuned against, and a gate fault by fault. Its settings are in [suite.json](../../evals/images/suite.json), its cases in [cases.json](../../evals/images/cases.json) and its fault questions in [faults.json](../../evals/images/faults.json). Since the request path became one image call ([ADR 0012](../../docs/adr/0012-one-image-call-from-the-text.md)) there is no text tier: `npm run evals:lean` ([scripts/evals/lean.mts](../../scripts/evals/lean.mts)) renders the cases through the request path's own assembly, from a frozen snapshot of each work's canon and reference sheets. A release folder holds a run's data, never a copy of the code.

Which check a change needs:

- **Every change:** `npm test`. [lean-engine-golden.test.ts](../../src/lib/__tests__/lean-engine-golden.test.ts) pins the exact prompt and references for five suite moments across the three works; a diff there names the works a change reaches. Regenerate it with `UPDATE_LEAN_GOLDEN=1` only as part of that change.
- **A change to the prompt, a style, a profile, the image model, or a release:** an image run (about $9 for 206 images on Nano Banana 2.1), scored blind against the last one, plus the [consistency](#consistency) pairing.

Steps, in order. Each refuses to overwrite what an earlier step wrote:

1. `npm run evals:lean -- plan --run <name> --from <suite text run> --model <id> [--cap <usd>]` writes `llm/releases/<name>/plan.json`: every image case (holdout first), the prompt version, the estimate and the cap the owner is asked to fund. `--from` names the run whose `snapshot.json` the cases are drawn from; the current one is [2026-11-07-suite-v3-text](../releases/2026-11-07-suite-v3-text/README.md). `--cases` and `--styles` narrow a pilot.
2. `npm run evals:lean -- run --run <name> --offline` rehearses with scripted replies, for free.
3. Commit `funding.json` (`authorization` quoting the owner, `operationCapUsd` equal to the plan's cap) with the plan, then `npm run evals:lean -- run --run <name> --execute` with `VISIBIBLE_EVAL_ENV_FILE` set. Each call reserves its most possible cost at catalog prices before it is sent, so spend cannot pass the cap. A content-filter refusal is that image's failure at no cost. A run that stops continues with `--resume` under what is left of the cap.
4. `npm run evals:lean -- blind --run <name> --baseline <dir> --baseline-images <dir> --batches <n>` mixes the candidate's images with a baseline run's into one blind pack judged against the moment's text, with `SCORING.md` beside it. Give each of two independent scorers every batch; they never see `key.json`.
5. `npm run evals:lean -- report --run <name> --scores <a files>,<b files> [--operator <file>]` settles the scores, writes `scoring/disputes.json` for the operator to rule on, and reports both arms by work, style, split and fault, the launch bar, and the gate with the baseline arm as baseline.

**Baselines.** The [lean-engine comparison](../releases/2026-11-09-lean-engine/README.md) holds the first lean measurement and the full engine's last, scored together. Keep a baseline's images (`evals/images/runs/<run>/`, outside git) until the next comparison is scored: a joint blind pack needs both arms' images.

**The gate.** On holdout items both runs judged, refusals, each fault and the unacceptable share may each rise by at most `max(5% of items, 2 items)` over the baseline. A different suite version, an unsettled score or a holdout item the candidate never ran fails it. It joins the per-image bar ([ADR 0006](../../docs/adr/0006-unseen-presence-speakers-and-launch-bar.md)), the consistency gate and owner sign-off; it replaces none of them.

**Small marks ([ADR 0006 amendment 7](../../docs/adr/0006-unseen-presence-speakers-and-launch-bar.md#amendment-7-small-marks-are-an-accepted-limitation)).** Scorers still answer `lettering`, and the suite gate still counts it. For the launch bar, an image whose only fault is small or unreadable marks counts as acceptable; readable words, captions and signatures do not. Because agreed scores never reach adjudication, the operator classifies every settled image whose only remaining fault is lettering in a separate file beside the run, as in the [v3 classification](../releases/2026-11-07-accept-small-marks/classification.json). The strict suite scores stay unchanged.

**Changing the suite.** Add cases, never replace them, and bump `version` in suite.json; a baseline and candidate must share a version. Mark a case `tuned` only if it shaped the engine before it joined. A new random case comes from a draw in suite.json, which the tests replay. A new work needs an import, a brief, a depiction profile, image styles and consistency groups, and an analysis: production's, or a committed fixture made with `--no-store`.

## Pilots

Narrow a run with `--cases` and `--styles` to try a prompt change on a few dev cases before a full run, as the [setting check](../releases/2026-11-09-lean-setting/README.md) did. Pilots are not release measurements and never use holdout cases. Nothing here authorizes spend: a paid run is the owner's decision under the cap it names.

## Consistency

The launch bar also checks that images that should agree do ([ADR 0008](../../docs/adr/0008-consistency-in-the-launch-bar.md)). [evals/images/consistency.json](../../evals/images/consistency.json) names the Bible's fixed groups, and `consistency.<work>.json` beside it Holmes's and Alice's. Character groups cover one canon entry across stories; setting groups cover neighbouring verses of one section. A suite image run renders every unit they name; pair one work at a time with `--groups <file>`. A lean run has no snapshot of its own, so pairing reads the run its plan names. To compare two runs on the same pairs, `npm run evals:lean -- pairing` writes both arms’ results alike, `pool` shuffles every set’s pairs into shared blind chunks and `unpool` returns the verdicts to each set. The gate's floors were set on the Bible and apply to it; the other works' rates are reported.

- `npm run evals:consistency -- pairs --results <results.ndjson>[,…] --out <dir>` ([scripts/evals/consistency.mts](../../scripts/evals/consistency.mts) over [consistency.ts](../../src/lib/image-evals/consistency.ts)) reads launch-matrix results with the `snapshot.json` beside each. Within each group and style, it pairs the shown images. A character pair needs the entry selected in both plans and the same canon stage. It checks every image against its recorded SHA-256 and writes `pairs.json` for scorers, `key.json` for the operator and one side-by-side picture per pair. The key also lists any group verse with no result row. `--images-root` finds images kept in another checkout.
- Two independent scorers judge every pair `same`, `different` or `unclear` from [the instructions](../../evals/images/consistency-scoring.md), blind to the key. The operator settles disagreements in a third file with the same shape, covering only the disputed pairs.
- `npm run evals:consistency -- report --out <dir> --scores <a>,<b> --operator <file> --styles <released styles> --baseline <previous report.json>` writes `report.json` and prints rates by kind and style, with the gate on the pooled released styles. The gate fails closed on a group verse the run never attempted, unsettled disputes, too few judged pairs, too many unclear pairs, a rate under its floor, or a fall of more than 10 points from the baseline. A refused verse counts as attempted.

Keep the pairs, key, scorer files, operator file and report in the release record beside the per-image scores. The [baseline](../releases/2026-10-29-consistency-baseline/README.md) shows the layout. For a release, pass the previous release's measurement as `--baseline`. For the Bible it is now the [Storybook release's](../releases/2026-11-01-storybook-consistency/README.md) `report.json` (four styles pooled). Suite runs' consistency reports, such as the [v3 baseline's](../releases/2026-11-07-suite-v3-image/README.md), are measurements to compare suite runs, not release baselines. The [first full measurement](../releases/2026-10-29-consistency-verses/README.md) shows how to carry verdicts for pairs already judged. Nothing here calls a model or spends.
